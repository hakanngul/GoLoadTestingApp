# GoLoad agent guide

GoLoad is a load-testing tool. A **test** is a YAML scenario (target, load profile, steps, thresholds). A **run** is one execution of a test, generated by GoLoad workers on the server (not on the user's machine). You talk to the GoLoad server through the tools below.

## Workflow (follow it in order)

1. `get_server_info` once: learn the caps (max users, max duration) and whether the target host is allowed.
2. `draft_test{url, goal}`: builds YAML from a URL and a goal. It does NOT save anything. Use `discover_links{url}` first if the user wants specific pages.
3. `try_test{yaml}`: runs ONE iteration and shows status, latency, redirects and hints. Read the hints (see below), fix the YAML, and try again until it is clean. `validate_test{yaml}` checks syntax only.
4. `create_test{name, yaml, data_file?}`: saves the test. Existing test: `update_test`.
5. Confirm with the user (see Safety), then `start_run{test, label?, users?, duration?}`.
6. `wait_run{run_id, timeout_s}` (repeat while it is still running), then `get_report{run_id}`.
7. Explain the result in plain words. For a before/after question use `compare_runs{run_ids}`; `set_baseline` marks a good run to compare against.

Other read tools: `list_tests`, `get_test`, `list_runs`, `get_run`, `list_suites`, `get_suite`, `get_suite_run`, `wait_suite_run`, `list_schedules`. Suites (`create_suite`, `run_suite`, `stop_suite_run`) run several tests together; `stop_run` aborts a run. In `--read-only` mode the mutating tools do not exist: say so and only explore.

Goals: `smoke` = quick check (few users, about 1 minute); `load` = normal day traffic; `stress` = find the limit; `spike` = sudden burst (for example a campaign moment).

## Scenario YAML essentials

Top level keys: `name`, `target`, `load`, `data`, `auth`, `steps`, `thresholds`, `regression`. Unknown keys are errors. Durations are strings such as `30s`, `5m`, `200ms`.

- `target.base_url` (required, absolute http/https), `headers`, `timeout` (default 30s). Cookies are kept per virtual user and redirects are followed by default.
- `load.model`: `closed` = a fixed number of users looping (stage `target` = users); `open` = arrival rate (stage `target` = iterations per second; `max_vus` caps concurrency). Stages ramp linearly from the previous target (0 at first). Prefer `closed` for "N people at the same time".
- `steps`: each has `name`, `method` (default GET), `path` (relative to base_url, may use `{{var}}`), optional `headers`, `body`, `think_time`, `extract`, `assert`.
- `extract`: `var`, `from` (`json` dot path like `data.items[0].id`, `header`, `regex` with first capture group), `expr`. Later steps use `{{var}}`.
- `assert`: `type` is `status`, `json` (with `expr`), `duration`, `body_contains`; `op` defaults to `eq` (also ne, lt, lte, gt, gte, contains); `value` is always a string.
- `thresholds`: `metric` is `latency.p50|p90|p95|p99|mean|max` (milliseconds), `error_rate` (fraction, 0.01 = 1%) or `rps`; `op` is lt, lte, gt, gte.
- `regression`: compares the run with the test's baseline; metrics `p50_ms p90_ms p95_ms p99_ms mean_ms max_ms error_rate rps`; set exactly one of `max_increase_pct`, `max_increase`, `max_decrease_pct`, `max_decrease`.
- `data`: `file` (CSV, header row = variable names) and `mode` (`sequential`, `random`, `unique`). The file is stored with the test; it does not have to exist when you only validate.
- `auth`: `type: login` (log in once per user and reuse the token), `bearer`, or `basic`. A login step needs at least one `extract`; the token is injected as `Authorization: Bearer {{token}}` into every step.

Example 1: closed model, simple page checks (what a "load" draft looks like).

```yaml
name: shop-load
target:
  base_url: https://shop.example.com
  timeout: 15s
load:
  model: closed
  stages:
    - duration: 30s
      target: 20
    - duration: 4m
      target: 20
    - duration: 30s
      target: 0
steps:
  - name: home
    path: /
    think_time: 2s
    assert:
      - type: status
        value: "200"
  - name: products
    path: /products
    think_time: 2s
    assert:
      - type: status
        value: "200"
thresholds:
  - metric: latency.p95
    op: lt
    value: 800
  - metric: error_rate
    op: lt
    value: 0.01
```

Example 2: open model with a chained step (extract an id, then use it) and a regression guard.

```yaml
name: api-flow
target:
  base_url: https://api.example.com
  headers:
    Accept: application/json
load:
  model: open
  stages:
    - duration: 10s
      target: 5
    - duration: 2m
      target: 5
  max_vus: 100
steps:
  - name: list products
    path: /products?limit=10
    extract:
      - var: product_id
        from: json
        expr: items[0].id
    assert:
      - type: status
        value: "200"
      - type: duration
        op: lt
        value: 500ms
  - name: product detail
    path: /products/{{product_id}}
    assert:
      - type: json
        expr: id
        op: eq
        value: "{{product_id}}"
thresholds:
  - metric: error_rate
    op: lt
    value: 0.01
regression:
  - metric: p95_ms
    max_increase_pct: 20
  - metric: error_rate
    max_increase: 0.005
```

Example 3: login with a data file. The CSV (`users.csv`, passed as `data_file` to `create_test`) has the header `username,password` and one account per row. Credentials live ONLY in the CSV, never in the YAML.

```yaml
name: account-load
target:
  base_url: https://app.example.com
load:
  model: closed
  stages:
    - duration: 20s
      target: 10
    - duration: 3m
      target: 10
data:
  file: users.csv
  mode: sequential
auth:
  type: login
  scope: per_user
  refresh: 15m
  login:
    path: /api/login
    headers:
      Content-Type: application/json
    body: '{"username": "{{username}}", "password": "{{password}}"}'
    extract:
      - var: token
        from: json
        expr: data.access_token
steps:
  - name: me
    path: /api/me
    think_time: 1s
    assert:
      - type: status
        value: "200"
thresholds:
  - metric: latency.p95
    op: lt
    value: 1000
```

Login forms that post form data (not JSON) use `Content-Type: application/x-www-form-urlencoded` and a body like `username={{username}}&password={{password}}`. `draft_test` with `login{...}` builds this for you.

## Reading try_test hints

- Redirect to a different host (for example example.com to www.example.com): set `base_url` to the final host and try again. Tell the user you changed it.
- 401 or 403: the page needs login (or blocks automation). Ask the user whether a test account exists; add `auth` with a data file.
- 429, a challenge page, or a WAF/CDN block (Cloudflare, Akamai): the site is rate-limiting or filtering the load generator. Do not try to evade it. Ask the user to allow the GoLoad worker IPs, or to test a staging environment.
- 404: wrong path; use `discover_links` to find real ones.
- Slow single iteration (seconds): warn that heavy load may hurt; start with a small run.
- Connection or TLS errors: check the URL; never set `insecure_skip_verify` unless the user says it is an internal test host.
- "Host not allowed" (allowlist rejection): the GoLoad server only permits listed hosts. Tell the user the server administrator must add the host to the allowlist. Do not look for workarounds.

## Safety rules

- NEVER call `start_run` or `run_suite` without an explicit user confirmation that names the users, the duration and the target host. "Run 20 users for 5 minutes against shop.example.com, ok?" then wait for a yes. A vague earlier "sure" does not count.
- Load tests can hurt real systems. Prefer staging; if the target looks like production (a public customer-facing domain), say so and let the user decide. Start small (smoke) before stress or spike.
- Never put passwords, tokens or API keys in the YAML or in chat. Credentials go into the data file (CSV) and are referenced as `{{column}}`. Ask the user to supply them; do not invent real-looking ones.
- Respect the caps from `get_server_info` (default 50 users, 10 minutes). The server refuses bigger runs. Do not split a run to get around caps.
- MCP runs are labeled automatically so the team can tell them apart. Add a useful `label` (for example the goal).
- Only test systems the user owns or is authorized to test.
- If a run misbehaves (errors climbing, the target slowing badly), call `stop_run`.

## Explaining results to non-experts

Lead with the verdict, then two or three numbers, then a suggestion. Avoid jargon.

- p95 latency: "95% of requests were faster than X ms". p50 is the typical request; p99 the slow tail.
- error rate: "about 2 of every 100 requests failed".
- rps: "the site handled about N requests per second".
- Thresholds passed or failed: say which and by how much.
- Stress runs: find the point where errors or latency jump and name the user count there ("it started struggling around 40 people at once").
- Look at the slowest or failing step in the report and name it in words ("the checkout page").
- Be honest about limits: one run is one data point; a smoke run says little about capacity.
- When comparing runs, say better, worse or the same and by roughly how much.
