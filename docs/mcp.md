# GoLoad MCP server (AI agents)

`goloadtest mcp` is a [Model Context Protocol](https://modelcontextprotocol.io) server that lets AI agents (Claude Code, Kiro, Cursor and other MCP clients) write and run load tests on a GoLoad server. It speaks MCP over stdio and calls the GoLoad REST API with a bearer token.

The agent can draft a test from a URL, try one iteration, save it, run it (after asking you), and explain the report in plain words. The built-in `create_load_test` prompt walks a non-expert through it with a few short questions, in the language you write in.

## How it fits together

```
AI client (laptop)  --stdio-->  goloadtest mcp (laptop)  --HTTPS + token-->  GoLoad server  -->  workers  -->  target site
```

- The MCP process runs on your machine, started by the AI client. It needs network access to the GoLoad server (for an internal server: connect the VPN first).
- The load itself is generated by the GoLoad server and its workers, never by your laptop.
- The server decides which target hosts are allowed (allowlist). If a host is rejected, the GoLoad administrator must allow it.

## Install

Build or download the `goloadtest` binary and put it on your `PATH` (the same binary that provides `serve` and `remote run`):

```
go build -o goloadtest ./cmd/goloadtest
```

Create an API token on the server (`serve -token`) and keep it in the environment:

```
export GOLOAD_TOKEN=...
goloadtest mcp --server https://goload.internal.example --token "$GOLOAD_TOKEN"
```

## Flags and environment

| Flag | Env | Meaning |
|---|---|---|
| `--server` | `GOLOAD_SERVER` | GoLoad server URL. |
| `--token` | `GOLOAD_TOKEN` | API token. Prefer the env var; flags show up in `ps`. |
| `--read-only` | | Hide every mutating tool (create/update/start/stop/baseline/suites). Good for exploration. `try_test` and `discover_links` stay available: they send one request per step to the target. |
| `--max-users` | | Refuse runs above this many users (default 50). |
| `--max-duration` | | Refuse runs longer than this (default 10m). |

The server's own limits still apply; the MCP caps can only be stricter.

## Client configuration

Example files are in [`examples/mcp/`](../examples/mcp/).

### Claude Code

```
claude mcp add goload -e GOLOAD_TOKEN="$GOLOAD_TOKEN" -- goloadtest mcp --server https://goload.internal.example
```

Or a project `.mcp.json` (Claude Code expands `${VAR}`):

```json
{
  "mcpServers": {
    "goload": {
      "command": "goloadtest",
      "args": ["mcp", "--server", "https://goload.internal.example"],
      "env": { "GOLOAD_TOKEN": "${GOLOAD_TOKEN}" }
    }
  }
}
```

### Kiro

`.kiro/settings/mcp.json` (workspace) or `~/.kiro/settings/mcp.json` (user). Config formats change between versions: check the Kiro docs for yours.

```json
{
  "mcpServers": {
    "goload": {
      "command": "goloadtest",
      "args": ["mcp", "--server", "https://goload.internal.example"],
      "env": { "GOLOAD_TOKEN": "${GOLOAD_TOKEN}" }
    }
  }
}
```

### Cursor

`.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global). Cursor expands `${env:NAME}`:

```json
{
  "mcpServers": {
    "goload": {
      "command": "goloadtest",
      "args": ["mcp", "--server", "https://goload.internal.example"],
      "env": { "GOLOAD_TOKEN": "${env:GOLOAD_TOKEN}" }
    }
  }
}
```

If your client does not expand variables, put the token in a user-level config file that is not in any repository, or start the client from a shell where `GOLOAD_TOKEN` is set (the MCP process inherits the environment).

## Security

- Keep the token in the environment or a user-level config, never in a repository. Use a token with only the access you need.
- Use `--read-only` when you only want the agent to look at tests and reports.
- Caps: the MCP server (`--max-users`, `--max-duration`) and the GoLoad server both refuse oversized runs. MCP runs are labeled so they are easy to spot in the run list.
- The agent is instructed to start a run only after you confirm users, duration and target host. Still review what it proposes.
- Secrets in tool output are masked. Do not paste passwords into the chat; test accounts go into the test's data file (CSV), not into the YAML.
- Everything the tools return (test YAML, reports, page content from `try_test`) is sent to your AI client's model provider. Do not use the MCP server with data you may not share with that provider.
- Only test systems you own or are authorized to test.

## Example conversation

```
You:    Write a load test for https://shop.example.com
Agent:  What should we find out? (a) Quick check, (b) Normal day traffic,
        (c) Find the limit, (d) Sudden burst. Default: (a)
You:    b
Agent:  How many people at the same time? (default 20)  How long? (default 5 min)
You:    ok
Agent:  Does the shop need a login for the pages that matter? (default: no)
You:    no
Agent:  I tried one visit: the home page redirected to www.shop.example.com, so
        I switched the test to that address. Both pages answered in under
        half a second. I saved it as "shop.example.com normal day".
        Start it now? 20 people at the same time, 5 minutes, against
        www.shop.example.com.
You:    yes
Agent:  ... Done. 95% of requests were faster than 410 ms and 0.2% failed, so
        the site handled a normal day fine. The slowest page was /products.
```

## Tool reference

| Tool | Mutating | What it does |
|---|---|---|
| `get_server_info` | no | Server version, caps, allowed hosts info. |
| `list_tests`, `get_test` | no | Browse saved tests. |
| `draft_test` | no | Build YAML from a URL and a goal (smoke, load, stress, spike). Does not save. |
| `discover_links` | no | Same-host links found on a page. |
| `validate_test` | no | Check YAML syntax. |
| `try_test` | no* | Run one iteration and show status, latency, redirects and hints. *Sends real requests to the target. |
| `list_runs`, `get_run` | no | Browse runs. |
| `wait_run` | no | Wait for a run to finish (with timeout). |
| `get_report` | no | Full report of a run. |
| `compare_runs` | no | Compare several runs. |
| `list_suites`, `get_suite`, `get_suite_run`, `wait_suite_run` | no | Browse and follow suites. |
| `list_schedules` | no | Scheduled runs. |
| `create_test`, `update_test` | yes | Save a test (optionally with a CSV data file). |
| `start_run`, `stop_run` | yes | Start (users, duration, label) or stop a run. |
| `set_baseline` | yes | Mark a run as the baseline for regression rules. |
| `create_suite`, `run_suite`, `stop_suite_run` | yes | Group tests and run them together. |

The MCP prompt `create_load_test` (argument: `url`) starts the guided conversation. The agent guide (workflow, YAML format, safety rules) is built into the server.
